# Регламент резервного копирования и восстановления (Backup & Restore) — РассрочкаПро

Финансовые данные, договоры рассрочки и история платежей требуют гарантированного механизма резервного копирования и проверенного восстановления.

---

## 1. Как устроена резервная копия в «РассрочкаПро»

1. **Предварительная сверка регистров (`reconcileFinance`)**:
   - Перед созданием снимка сервер автоматически сверяет балансы счетов (`financial_accounts`) с суммой подтверждённых проводок (`ledger_entries`), суммы распределений платежей (`payments` vs `payment_allocations`) и суммы графиков договоров (`contracts` vs `schedule_items`).
   - Если обнаружено хотя бы одно расхождение на 1 копейку, создание повреждённой копии блокируется.
2. **Полный снимок таблиц**:
   - В снимок включаются таблицы: `users` (без хешей паролей), `installment_plans`, `settings_history`, `clients`, `suppliers`, `purchases`, `contracts`, `schedule_versions`, `schedule_items`, `overdue_contacts`, `financial_accounts`, `payments`, `payment_allocations`, `ledger_entries`, `documents` (метаданные и `SHA-256`).
3. **Аутентифицированное шифрование (`AES-256-GCM` + `SHA-256`)**:
   - Сериализованный JSON шифруется ключом `BACKUP_ENCRYPTION_KEY` (256 бит) с уникальным 12-байтным `IV` и 16-байтным тегом подлинности `authTag`.
   - Дополнительно вычисляется `SHA-256` открытого текста (`sha256Hash`).
   - Файл сохраняется в приватном каталоге `./backups/backup_<timestamp>_<id>.enc.json` с правами доступа `0600`.

---

## 2. Создание, скачивание и проверка копии через интерфейс (Раздел 14)

Доступно только пользователю с ролью **Владелец (`owner`)**:

1. Откройте раздел **«14. Безопасность и бэкапы»**.
2. Нажмите кнопку **«Создать резервную копию»** (`POST /api/v1/security/backups`).
3. Нажмите кнопку **«Проверить целостность»** (`POST /api/v1/security/backups/:id/verify`):
   - Сервер считывает файл с диска, расшифровывает `AES-256-GCM`, сверяет `SHA-256` и проверяет инварианты финансовых регистров внутри архива.
4. Нажмите кнопку **«Скачать»** (`GET /api/v1/security/backups/:id/download`), чтобы сохранить зашифрованный файл `.enc.json` на внешний носитель (компьютер/облачный диск владельца).

---

## 3. Создание и проверка резервной копии через CLI

Выполните в корне проекта:
```bash
npm run db:inspect
```
Эта команда:
- выводит полную инвентаризацию всех таблиц базы данных;
- автоматически создаёт новую зашифрованную резервную копию в `./backups/`;
- немедленно выполняет тестовую расшифровку и проверку `SHA-256` и финансовых регистров.

---

## 4. Полное восстановление базы данных из резервной копии

### Способ 1. Через веб-интерфейс администратора
1. Войдите под учётной записью владельца (`owner`).
2. Откройте раздел **«14. Безопасность и бэкапы»**.
3. В строке нужной резервной копии нажмите **«Восстановить БД»** (`POST /api/v1/security/backups/:id/restore`).
4. Что происходит на сервере внутри атомарной транзакции (`BEGIN IMMEDIATE TRANSACTION`):
   - Проверяется подлинность тега `AES-256-GCM` и `SHA-256` архива.
   - Очищаются текущие операционные таблицы в обратном порядке внешних ключей.
   - Загружаются все записи из архива (`installment_plans`, `financial_accounts`, `clients`, `suppliers`, `purchases`, `contracts`, `schedule_versions`, `schedule_items`, `overdue_contacts`, `payments`, `payment_allocations`, `ledger_entries`).
   - Выполняется контрольная сверка `reconcileFinance(db)`. Если регистры не сходятся, транзакция автоматически откатывается (`ROLLBACK`).
   - В журнал аудита записывается событие `BACKUP_RESTORE_EXECUTED`.

### Способ 2. Подтверждённый автоматический тест восстановления
Полный цикл **Создание копии -> Очистка базы данных -> Восстановление из копии -> Сверка всех договоров, клиентов и балансов** автоматически проверяется в каждом прогоне:
```bash
npm test
```
(См. тест №6 в `tests/finance_and_security.test.ts`).
