# DECISIONS.md — Архитектурные решения (ADR)

## ADR-001: Сохранение и развитие существующего стека (TypeScript / Express / React / SQLite + PostgreSQL DDL)
- **Контекст**: В п. 3 ТЗ указан предпочтительный стек (Go + Gin + PostgreSQL + React + TypeScript + Vite), но также содержится прямое правило: *«Сначала проверь существующий стек. Если проект уже использует другие технологии, не меняй их автоматически. Обоснуй необходимость миграции и предложи безопасный план»*.
- **Аудит окружения**: Текущая среда исполнения базируется на Node.js v22.23.4 (`express`, `tsx`, `vite`, `react`, `typescript`) и не содержит компилятора Go. При этом Node.js v22 предоставляет встроенный синхронный реляционный движок `node:sqlite` (`DatabaseSync`) с полноценной поддержкой ACID-транзакций, внешних ключей и `CHECK`-ограничений.
- **Решение**:
  1. Сохранить работающий рантайм Node.js + TypeScript + Express + React 19 + Vite, построив строгий модульный монолит с чётким разделением слоёв (`routes` → `finance/security/audit` → `db`).
  2. Подготовить каноническую SQL-миграцию для PostgreSQL (`migrations/001_init_postgres.sql`), полностью совместимую по модели данных, чтобы при переносе на внешний выделенный сервер с Go/PostgreSQL или Node/PostgreSQL схема данных переносилась 1-в-1.

## ADR-002: Представление денег исключительно в целых копейках
- **Контекст**: Операции с числами с плавающей точкой (`IEEE 754 float/double`) приводят к накоплению ошибок округления (например, `0.1 + 0.2 = 0.30000000000000004`).
- **Решение**: Все денежные значения в БД, API и бизнес-логике хранятся и передаются как целые числа копеек (`INTEGER` / `BIGINT`). Форматирование в рубли и копейки (`12 500,00 ₽`) выполняется только на уровне отображения, а ввод пользователя переводится в копейки детерминированным парсером.

## ADR-003: Версионирование графиков платежей и настроек рассрочки
- **Контекст**: Изменение тарифов рассрочки не должно менять ранее заключённые договоры, а реструктуризация договора не должна затирать исходный график.
- **Решение**:
  1. В таблице `contracts` сохраняются зафиксированные на момент подписания значения `markup_percent`, `down_payment_percent`, `rounding_rule` и `plan_version`.
  2. Таблица `schedule_items` содержит поле `schedule_version`. При реструктуризации создаётся запись в `schedule_versions` с новой версией, старые строки получают статус `superseded`, а в новой версии переносятся уже оплаченные платежи и перестраивается остаток графика.

## ADR-004: Отказ от автоматического FIFO-распределения частичных платежей
- **Контекст**: Бизнес-требование №6 прямо запрещает автоматическое распределение поступивших сумм по старейшему долгу без явного выбора владельца.
- **Решение**: Любое поступление от клиента создаёт запись в `payments` с полем `unallocated_kopecks`. Распределение выполняется только через явное указание целевых `schedule_item_id` и сумм (при создании платежа с явно выбранными строками графика либо позже через диалог ручного распределения).
